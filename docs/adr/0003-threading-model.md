# ADR-0003: Threading model for the Qt GUI and the async engine

Date: 2026-05-29
Status: Proposed (until verified by integration testing)

## Context

The engine vendored per ADR-0001 is async end to end (`async def` everywhere, driven by Playwright and `asyncio`). Qt, per ADR-0002, requires that every widget update happen on the main thread; touching a `QWidget` from another thread is undefined behaviour and crashes on macOS more often than not. A single application takes 30 to 120 seconds wall-clock (LLM scoring, docx to pdf tailoring, browser-automated form fill), so running it on the GUI thread freezes the window for the duration, which the user will read as a hang. There are two real options for combining a Qt event loop with an asyncio engine. Option (a) is `qasync`, a single asyncio loop that drives both Qt event dispatch and engine IO from one thread; option (b) is a dedicated `QThread` worker that owns its own asyncio loop and communicates with the GUI via Qt signals. Option (a) is appealing because there is only one loop to reason about, but it couples UI responsiveness to engine health: when Playwright stalls (and it does, on slow Seek pages and on resume uploads), the same loop that is supposed to repaint the window is blocked waiting on the browser. Option (b) gives up the elegance of a single loop in exchange for isolation; a hung engine cannot freeze the GUI because they are not sharing a scheduler.

## Decision

Adopt option (b): a dedicated worker thread that owns its own asyncio loop. `EngineWorker(QObject)` lives on a `QThread`, exposes Qt signals `started`, `progress(ProgressEvent)`, `finished(ApplicationResult)`, and `failed(str)`, and exposes one public slot `run_job(job_url, allow_real_submit)` which the GUI invokes via `QMetaObject.invokeMethod` so the cross-thread call is serialized through Qt's queued-connection machinery. Inside the worker, `asyncio.new_event_loop()` creates a loop pinned to the worker thread, and the slot runs `loop.run_until_complete(apply_to_job(...))` on the adapter from ADR-0001. Cancellation has two layers: between adapter stages a cooperative `is_cancelled` callable is checked, and in-flight tasks are torn down via `asyncio.Task.cancel()` which propagates `CancelledError` into Playwright and closes the browser context in a `finally` block. The worker is a singleton because the safety gate in ADR-0004 is process-global module state and two workers would race on it, and because the engine itself is not parallel-safe per ADR-0001.

## Consequences

The GUI thread is never blocked by engine work, so the window stays responsive even when Playwright hangs on a slow page. All widget updates flow through Qt signals, so the rule "never touch a widget off the GUI thread" is enforced by the seam itself rather than by convention. The price is two execution contexts to reason about instead of one, and the discipline that every new engine call goes through the slot rather than being invoked directly from the GUI. A second worker is structurally forbidden; if parallelism is ever wanted, it requires a separate ADR because both the safety gate and the engine state would need to change. The cancellation path is well-defined but relies on Playwright honouring `CancelledError` quickly; if it does not, the worker falls back to forcing a browser-context close, accepted as a last-resort tear-down.
