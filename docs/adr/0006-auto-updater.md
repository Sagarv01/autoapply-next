# ADR-0006: Auto-update mechanism

Date: 2026-05-29
Status: Proposed (until verified by integration testing)

## Context

The app runs on user machines under the user's real Seek session, so an update is privileged code execution; a malicious or corrupt update payload is a remote code execution path against every user who installs it. ADR-0002 accepted that PySide6 has no plug-and-play equivalent to `electron-updater`, so the updater is something we own rather than something we inherit. The constraint, written in capitals on the user's prompt, is "do not hand-roll crypto"; the update payload must be signature-verified against pinned root keys before the binary swap, and the verification code must be a library that other people audit, not something we wrote. Options evaluated. `tufup` is a thin Python wrapper around TUF (The Update Framework), a well-tested signature and role model used by PyPI's warehouse and several language ecosystems; cross-platform, GitHub Releases as the artefact feed, growing community, mature enough for a single-user desktop tool. Sparkle (macOS) plus WinSparkle (Windows) are platform-native, very mature, ed25519-signed, but require Python wrappers (`pyobjc` for Sparkle, `ctypes` for WinSparkle) and force us to maintain two systems with two key infrastructures instead of one. An electron-updater equivalent in the Python world does not exist. A bespoke updater is excluded by the do-not-hand-roll-crypto rule.

## Decision

Adopt `tufup`. One Python codebase, one update workflow, one set of signing keys. Operationally: a tag-triggered GitHub Actions build produces signed binaries (per ADR-0005) plus the `tufup` metadata (`metadata.json` and the `targets/` directory), and the workflow publishes them to a GitHub release. The app polls for updates on startup with a 24-hour cache, and the user can force a check from Settings. Updates are atomic: download to a staging directory, verify the signature against the pinned root keys baked into the app, swap the installed bundle on next launch. TUF requires four role keys (root, targets, snapshot, timestamp); the root key is generated offline and stored air-gapped, while the targets, snapshot, and timestamp keys live in GitHub Actions secrets so the CI can sign each release. The initial key ceremony is a one-off operator task documented in the README, not something that re-runs per release. If the update server is unreachable, the app keeps running on the installed version with a quiet log line; if signature verification fails, the update is rejected, a Sentry breadcrumb is recorded, and the user is never silently rolled back to a possibly-tampered binary.

## Consequences

The crypto path is library code (`python-tuf` via `tufup`) that we configure rather than write, which satisfies the non-negotiable. The four-role key model is heavier than a single signing key, but the audit story is "we use TUF as designed" rather than "we invented a key model," which is exactly the trade we want. GitHub Releases as the feed is free, well-understood, and integrates with the build pipeline in ADR-0005. The 24-hour startup poll is cheap, the user-triggered check in Settings covers the urgent-update case, and the on-next-launch swap avoids the user-interrupting "restart now" prompt. The root-key ceremony is a real operational obligation; it is documented in the README and is a one-off rather than a recurring tax. If `tufup` ever stops being maintained, migration to Sparkle plus WinSparkle remains an option, but the cost of switching is bounded because the engine, adapter, and Qt code are unaffected.
