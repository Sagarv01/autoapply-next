# ADR-0005: Packaging and code-signing strategy

Date: 2026-05-29
Status: Proposed (until verified by integration testing)

## Context

The deliverable per ADR-0002 is a signed, cross-platform PySide6 desktop app for macOS arm64, macOS x64, and Windows x64. The app depends on Playwright, which itself depends on a Chromium build that is not pip-installable in the normal sense; it is fetched by `playwright install chromium` and lives outside `site-packages`. Three packaging tools were evaluated. PyInstaller is the most mature in the Python ecosystem, handles PySide6 cleanly via maintained hooks, supports single-file and one-dir outputs on both platforms, and has a well-trodden signing path; it does not bundle Playwright's Chromium by default, so the choice is to either write explicit hooks that copy the browser into the bundle (about 150 MB added per release, and the bundle stops being a clean signed unit because the Chromium binary is not signed by us) or defer Chromium acquisition to first run. Briefcase (BeeWare) is a higher-level wrapper that packages and signs in one step, attractive in theory; in practice it is less mature on Windows, opinionated about the project layout in ways that fight a vendored engine subtree, and gives less control over Chromium handling. Nuitka compiles Python to C and produces smaller binaries, but builds take 10+ minutes on CI, the combination of Playwright and PySide6 is brittle in Nuitka's static-analysis pipeline, and the Windows ecosystem is thinner. None of the three solves the Authenticode requirement that Windows signing now uses an EV cert or an HSM-backed flow (SSL.com eSigner or DigiCert KeyLocker); that is a vendor decision the user makes once and the CI consumes via secrets.

## Decision

Use PyInstaller. Build a one-dir bundle on each platform, sign on macOS via `codesign --options runtime` followed by `notarytool submit --wait` and `xcrun stapler`, sign on Windows via `signtool sign /fd SHA256 /tr <timestamp_server>`. Defer Chromium to first run: ship a small first-run wizard in the Settings screen that calls `playwright install chromium` after sign-in, document the behaviour in Settings and the README, and surface a clear progress UI because the download is around 150 MB and the user should know what is happening. If signing certificates are absent (developer build, contributor without secrets), the build still produces an unsigned dev artefact and emits a `MISSING_CERTS` notice in the build log; this keeps local iteration fast and makes the CI failure mode loud rather than silent. Document the Windows signing-cert vendor choice (EV cert via SSL.com eSigner or DigiCert KeyLocker) and the exact secret names the CI workflow needs, so the operator can provision them once.

## Consequences

PyInstaller is well documented and well understood, which lowers the on-call burden when packaging breaks; the explicit hooks for PySide6 are maintained upstream rather than something we own. Deferring Chromium keeps the release artefact small, keeps the signed bundle a clean signed unit, and avoids re-uploading 150 MB on every release for a binary that does not change between releases; the cost is a slower first-run experience and a hard dependency on network at first launch, which the wizard surfaces honestly rather than hiding. Signing identities from the old `autoapply.com.au` project (if the user owns them) are reused as-is; only the build commands change. The unsigned-dev-artefact path means contributors without secrets can still produce a working binary, which lowers the bar for code review on the build pipeline. If Briefcase's Windows story matures, or if a future packaging need is genuinely better served elsewhere, switching is a one-ADR change because the engine, adapter, and Qt code are framework-agnostic.
