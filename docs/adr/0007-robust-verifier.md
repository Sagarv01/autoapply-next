# ADR-0007: Robust verifier wrap around `seek_apply._verify_applied`

Date: 2026-05-31
Status: Accepted

## Context

The user's first real submission via the GUI succeeded on Seek (the job is visible on the Applied Jobs page) but the engine's `_verify_applied` returned False with "Submission not verified on Applied Jobs page ... likely failed ... Marking as failed for manual retry." That is a false negative. Root cause traced from `~/Library/Logs/AutoApply Next/autoapply-next.log`: the engine reported `Verify attempt 1/3: 'Seek listing 92421026 @ ' not yet in 20 cards`. The adapter's `_peek_and_fetch_listing` was constructing the `JobListing` with `title="Seek listing 92421026"` (a placeholder) and `company=""` (empty). The engine's `_verify_applied` requires a fuzzy substring match on both axes; with an empty target company, every match call short-circuits to False. The fault sits at the GUI to engine boundary, not in the engine itself; the engine's daemon scrapes proper title and company in `scraper/seek.py` and the daemon's verifies pass. Beyond that immediate cause, the engine treats a failed verify as a definite failure and asks for "manual retry," which is a duplicate-submission risk that no automated loop can take safely.

## Decision

Two changes, both at the integration boundary; the engine source under `vendor/job-finder/` is not touched. First, the adapter's `_peek_and_fetch_listing` now reads the title and company from the `applications` row in `jobs.db` when one exists (the scraper writes real values; this is the common case for Queue-selected jobs); only falls back to a URL-derived placeholder when the URL has never been scraped. Second, a new `RobustVerifier` (`src/autoapply_next/engine/verifier.py`) monkey-patches `seek_apply._verify_applied` for the duration of one apply, in the same pattern as `safety.SafetyGate._submit`. The patched function polls the Applied Jobs page with backoff over a 30 second window and tries two match strategies: by canonical Seek job id present in any `<a href>` on the page (most robust, since job ids do not suffer from "via Seek" suffixes or recruiter renames or text truncation), and by normalized title + company as a fallback. The wrap exposes three outcomes through a `last_state.outcome` field on the verifier object: `APPLIED` (found), `NOT_APPLIED` (cards readable and absent after the full window), and `UNCERTAIN` (every poll failed to load the page). The wrap returns `True` for both APPLIED and UNCERTAIN so the engine never raises `SeekApplyError` on an inconclusive verify; the adapter reads `last_state.outcome` and maps UNCERTAIN to a new `ApplicationStatus.SUBMITTED_UNCERTAIN` ("submitted, needs manual check"). UNCERTAIN never becomes FAILED. NOT_APPLIED stays FAILED. The auto-retry path simply does not exist for any of the three; the batch flow's `run_batch` already iterates each URL exactly once and never re-submits.

## Consequences

The user's just-submitted job (92421026) was reconciled by a one-shot script (`scripts/reconcile_92421026.py`) that flipped its `applications` row from `queued` to `applied` with a note. Future GUI submissions get real metadata from `jobs.db` plus the robust verifier; the cause that produced this report cannot recur in the same shape. The wrap is dormant in dry-run mode because `safety.SafetyGate` raises `DryRunReached` before `_verify_applied` runs; no behaviour change for the existing dry-run paths. New status `SUBMITTED_UNCERTAIN` flows through `ApplicationResult` to the Results screen and the batch tally; UI surfaces of those should grow a distinct treatment for it in a follow-up so the user can find the rows that need manual checks. The engine itself still has the original `_verify_applied` (two-state, fuzzy text-only matching) and would benefit from a job-id strategy and a three-state outcome on its own; that is an upstream improvement, not a blocker. If we ever sync the vendored copy at a new commit, this ADR plus the runtime wrap remain valid as long as the engine still exposes `_verify_applied(page, job_title, job_company)` and `_Journal._data["url"]`; a contract test (`tests/contract/test_verifier.py`) should be extended with a drift-detection assertion against those names the next time we re-vendor.
